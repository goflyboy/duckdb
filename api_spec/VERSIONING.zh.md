# C API 版本管理

`duckdb.h` 和 `duckdb_extension.h` 都从规范中记录的同一份生命周期生成，因此两者
永远不会在符号何时出现或何时稳定上产生分歧。
以某个版本为目标会得到该版本时的 API，但 `duckdb.h` 的直接使用者和使用 `duckdb_extension.h` 的扩展之间存在一些细微差异，
因为扩展还需要固定的 ABI 布局。

## 生命周期

API 规范中的每个条目都携带一个带日期的状态转换栈，最新的在前：

```yaml
lifecycle:
  - [ "stable", "v1.5.6", "2026-07-30" ]
  - [ "unstable", "v1.4.0", "2025-09-12" ]
```

目前有四种状态，语义如下：

| 状态 | 含义 |
|------|------|
| `unstable` | 存在但不作承诺；可能在不通知的情况下更改或消失 |
| `stable` | 已承诺；签名和 ABI 槽位从此冻结 |
| `deprecated` | 仍被承诺，但计划移除；调用方应迁移 |
| `removed` | 已从库中移除 |

每个函数__必须__声明生命周期。函数在扩展 v-table 中的槽位由它被
稳定时的版本定义（如果不稳定则在末尾），因此没有日期的函数将没有确定的位置。

## `duckdb.h` 的使用者

例如，直接链接 `libduckdb` 的客户端库或应用程序。
链接 DuckDB 时，声明没有必须保持的固有顺序，因此可以独立地按版本
门控。
要控制哪些符号对您可见，可以定义以下宏：

- `DUCKDB_API_VERSION_MAJOR` / `_MINOR` / `_PATCH`

这是您想要目标化的 API 版本。
默认为头文件描述的最新版本。请定义全部三个或都不定义。
只有在该版本时已经稳定的声明才会出现。这允许您"获取版本 X 时的 API"。

- `DUCKDB_API_ALLOW_DEPRECATED`

默认为 `1`。设置为 `0` 后，*截至您的目标版本*已弃用的任何内容都会消失，以便编译器找出您剩余的
使用。
弃用是相对于目标的，在 v1.5.6 中弃用的符号对于目标为 v1.5.4 的构建仍然可见。

- `DUCKDB_API_ALLOW_UNSTABLE`

默认为 `0`。设置为 `1` 以显示尚未稳定的符号，并接受它们可能更改。
这要求目标为最新版本，见下文。

为向后兼容，较旧的 `DUCKDB_API_NO_DEPRECATED` 和 `DUCKDB_EXTENSION_API_VERSION_UNSTABLE` 宏
仍然有效，它们只是相应地设置新的 `DUCKDB_API_ALLOW_DEPRECATED`/`DUCKDB_API_ALLOW_UNSTABLE` 宏。

### Unstable 是它自己的一个版本

符号从它被**稳定**的版本开始发出，而不是它被引入的版本。
在此之前，它不属于任何已发布版本：其签名仍可能更改。
因此，同时要求较旧的目标*和* unstable 表面，会在该版本从未承诺的名称下给您今天的签名，
这是"版本 X 时的 API"唯一不成立的情况。
因此两者互斥：

```c
#if DUCKDB_API_ALLOW_UNSTABLE && !DUCKDB_API_VERSION_AT_LEAST(1, 5, 6)
#error "the unstable surface requires targeting the newest API version"
#endif
```

这为*两种使用者*留下一条规则：
- **选择一个版本**，获得截至该版本已稳定的表面，签名冻结且弃用相对于该版本，或者，
- **选择 unstable**，获得最新版本的所有内容，包括不稳定符号，但不作任何承诺。

因此门控只会读取 `DUCKDB_API_VERSION_AT_LEAST(<stabilized>)`，或对尚未
稳定的内容使用裸开关。

## 扩展

扩展（未静态链接时）不直接链接引擎符号。它接收一个函数
指针结构体，每次调用都通过一组"间接"宏穿过它。
扩展加载时，该结构体被复制到全局静态变量：

```c
duckdb_ext_api = *res;   /* 复制扩展结构体的 sizeof */
```

如果扩展期望的结构体是 DuckDB 实际传递结构体的**前缀**，则该复制是合理的，
因此结构体的布局是 ABI 的一部分，不能依赖引擎看不到的任何内容。

### V-Table 结构体是有版本的

v-table 中的函数按函数被**稳定**的版本分组为连续区段，而不是
它被引入的版本。
每个区段在单个门控下发出：

```c
typedef struct {
	/* v1.2.0 区段 — 404 个槽位，始终存在 */
#if DUCKDB_API_VERSION_AT_LEAST(1, 5, 6)
	/* v1.5.6 区段 — 142 个槽位 */
#endif
#if DUCKDB_API_ALLOW_UNSTABLE
	/* 任何未来的不稳定函数，始终在末尾 */
#endif
} duckdb_ext_api_v1;
```

因此，以较旧版本为目标会将结构体截断为 DuckDB 当时发布的精确槽位。
可以使用 `scripts/check_extension_abi.py` 对照每个发布标签验证这一点。

由于 Extension-C-API 结构体最初是在 **v1.2.0** 版本引入的，因此任何内容都不可能早于它，
以更旧版本为目标会是编译错误，而不是空结构体。

### 同样的两个选择，由构建系统做出

上文"[Unstable 是它自己的一个版本](#unstable-是它自己的一个版本)"一节中解释的规则在此不变地适用：**选择一个版本**，或**选择 unstable**。
不同之处在于，扩展不自己设置宏，而且该选择不仅关乎它能看见哪些符号：
它还决定哪些 DuckDB 版本可以加载结果。

因此，您调用的 cmake 构建辅助函数会替您做出选择：

**版本化**：可向前加载

```cmake
build_loadable_extension_capi(my_ext 1 5 6 ${SOURCES})
```

ABI 类型 `C_STRUCT`。您声明所需的最低 API 版本（这会隐式设置
`DUCKDB_EXTENSION_API_VERSION` 宏）。
任何等于或高于它的 DuckDB 都可以加载您的扩展。您会得到 v-table 到该目标版本的前缀，
仅此而已。
请固定拥有您所需功能的*最低*版本：v1.2.0 到 v1.5.6 之间没有任何内容被稳定，因此介于两者之间的每个固定值
都会产生同样的 404 个槽位，同时不必要地排除之前的 DuckDB。
根据上述规则，`DUCKDB_API_ALLOW_UNSTABLE` 不可用。
`DUCKDB_API_ALLOW_DEPRECATED` 仍然有效：禁用它只会删除*名称*（间接宏）而不删除槽位，因此
它隐藏符号而不打乱 v-table 布局。

**固定**：锁定到特定 DuckDB 版本

```cmake
build_loadable_extension_capi_unstable(my_ext ${SOURCES})
```

ABI 类型 `C_STRUCT_UNSTABLE`。您__不能__设置任何版本宏。
您会得到完整的 v-table 结构体，以及尚未稳定的尾部。
DuckDB 只有在与您构建时所用版本完全相同时才会加载您的扩展（由扩展元数据
页脚中记录的版本强制执行）。
此类构建向 `get_api` 报告确切版本，而不是语义版本，例如发布标签，或开发构建的 git 提交
哈希，取自构建系统设置的 `DUCKDB_EXTENSION_API_VERSION_UNSTABLE`。

### 为什么我不能同时获得不稳定符号_并_固定版本？

一般原因如上：不稳定签名不会被冻结，因此没有版本可以承诺它。
但对扩展来说这一点尤其重要，因为 v-table 的不稳定尾部位于每个版本区段之后，
因此其槽位偏移取决于所有稳定版本都先被编译进来。
一个既固定 v1.2.0 *又*编译尾部的扩展会将其第一个尾部槽位放在索引 404，而 DuckDB 将其放在 546，
每次不稳定调用都会静默地通过错误的指针。
`duckdb.h` 已经发出的保护也能防止这一点。

这在实践中没有代价，因为唯一能到达尾部的构建本来就锁定到特定 DuckDB 版本。

这也意味着槽位在它被**稳定**时冻结，而不是在它被引入（作为不稳定）时冻结。
当函数不稳定时，它只会被锁定到单个版本的构建观察到，因此它仍然可以被
重新排序、更改签名或完全删除。
一旦它被设置为 `stable`，其槽位就是永久的。

在添加 C-API 函数时，这一点很重要：一个开发中的函数如果被证明是错误的，
必须在它的 `stable` 版本发布**之前**修复，否则它将永久占用一个槽位。

### 重命名

我们应尽可能避免重命名函数，但不幸的是已经发生过几次。
重命名的符号保留其槽位和签名，仅更改拼写，因此它 ABI 兼容但
源码不兼容。
这可以记录在规范中：

```yaml
create_bignum:
  renamed_from: { name: create_varint, version: "v1.4.0" }
```

旧拼写随后会作为门控为 `BELOW` 该版本的别名发出（类型用 `typedef`，函数用 `#define`），
因此只有在您目标为仍包含它的版本时才可达，一旦目标为重命名它的版本就消失。
别名位于 `duckdb.h` 中，扩展头文件包含它，并且它自己的映射宏链会穿过别名，
因此重命名的函数仍通过 vtable 而不是库符号解析。

`scripts/check_extension_abi.py` 会从生成的头文件中读回这些别名，因此重命名不会读成
之后每个槽位都发生了偏移，未来的重命名也不需要更改检查器。

### 移除

`removed` 函数必须保留其槽位，以免其后的偏移移动，但它会失去映射宏，因此
名称不再可编译。
DuckDB 可以自由地将实际函数指针保留为 `NULL`。

请注意，移除是唯一可能破坏*已经构建*的扩展的事情：其槽位索引已固化，
而较新的 DuckDB 会使该槽位为 `NULL`，因此调用会崩溃而不是编译失败。
版本管理方案中没有任何东西能防止这一点，因为扩展在移除存在之前就已编译。
优先使用弃用，它在运行时不产生代价：槽位保持填充，旧二进制继续工作，而新构建会
得到编译错误。

## 版本宏转发

`duckdb_extension.h` 会解析 `DUCKDB_EXTENSION_API_VERSION_*`，并在包含 `duckdb.h` 之前将其转发为 `DUCKDB_API_VERSION_*`。
否则，`duckdb.h` 会声明最新表面，而映射宏却遵循扩展较旧的目标，
并且宏缺失的名称会静默解析为真实的 `duckdb.h` 声明，使可加载
扩展直接引用引擎符号。
转发使两者保持同步，因此此类名称会变成编译错误。同样，将两者显式设置为
不同值会被拒绝。
